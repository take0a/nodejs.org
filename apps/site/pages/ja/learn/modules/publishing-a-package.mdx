# パッケージの公開

提供されているすべての `package.json` 設定（「動作しない」と明記されていないもの）は、Node.js 12.22.x（v12 最新、サポートされている最も古いバージョン）と、当時の最新バージョンである 17.2.0[^1] で動作します。ちなみに、webpack はそれぞれ 5.53.0 と 5.63.0 でも動作します。これらの設定は [JakobJingleheimer/nodejs-module-config-examples](https://github.com/JakobJingleheimer/nodejs-module-config-examples) から入手できます。

好奇心旺盛な方は、[How did we get here](#how-did-we-get-here) と [Down the rabbit-hole](#down-the-rabbit-hole) で背景とより詳しい説明をご覧ください。

## 修正方法を選択してください

ほぼすべてのユースケースをカバーする2つの主な選択肢があります。

- ソースコードをCJSで記述して公開する（`require()`を使用します）。CJSはCJSとESMの両方で使用できます（Node.jsのすべてのバージョン）。[CJSのソースコードと配布](#cjs-source-and-distribution)に進んでください。
- ソースコードをESMで記述して公開する（`import`を使用し、トップレベルの`await`は使用しません）。ESMはESMとCJSの両方で使用できます（Node.js 22.xおよび23.xの場合。[ESモジュールの`require()`](https://nodejs.org/api/modules.html#loading-ecmascript-modules-using-require)を参照してください）。[ESMのソースコードと配布](#esm-source-and-distribution)に進んでください。

一般的には、CJSまたはESMのいずれか1つの形式のみを公開するのが最善です。両方を公開する必要はありません。複数の形式で公開すると、[二重パッケージの危険性](#二重パッケージの危険性)やその他のデメリットが発生する可能性があります。

主に歴史的目的のために、他にも選択肢があります。

### CJS のソースと配布

最小限の設定は [`"name"`](https://nodejs.org/api/packages.html#name) のみで十分でしょう。しかし、難解でないほど良いでしょう。基本的には、`"exports"` フィールド/フィールドセットを使用してパッケージのエクスポートを宣言するだけです。

**動作例**: [cjs-with-cjs-distro](https://github.com/JakobJingleheimer/nodejs-module-config-examples/tree/main/packages/cjs/cjs-distro)

```json displayName="Minimal package.json"
{
  "name": "cjs-source-and-distribution"
  // "main": "./index.js"
}
```

```json displayName="Advanced (verbose) package.json"
{
  "name": "cjs-source-and-distribution",
  "type": "commonjs", // current default, but may change
  "engines": { "node": ">=12.22.7" },
  "exports": {
    ".": "./dist/index.js",
    "./package.json": "./package.json"
  }
}
```

`packageJson.exports["."] = filepath` は `packageJson.exports["."].default = filepath` の省略形であることに注意してください。

### ESM のソースと配布

シンプルで、実績があり、確実な方法です。

Node.js v23.0.0 以降では、静的 ESM（トップレベルの `await` を使用しないコード）を `require` できるようになりました。詳細は、[`require()` を使用した ECMAScript モジュールのロード](https://nodejs.org/api/modules.html#loading-ecmascript-modules-using-require) を参照してください。

これは、上記の CJS-CJS 構成とほぼ同じですが、[`"type"`](https://nodejs.org/api/packages.html#type) フィールドという小さな違いが 1 つあります。

**動作例**: [esm-with-esm-distro](https://github.com/JakobJingleheimer/nodejs-module-config-examples/tree/main/packages/esm/esm-distro)

```json displayName="Minimal package.json"
{
  "name": "esm-source-and-distribution",
  "type": "module"
  // "main": "./index.js"
}
```

```json displayName="Advanced (verbose) package.json"
{
  "name": "esm-source-and-distribution",
  "type": "module",
  "engines": { "node": ">=12.22.7" },
  "exports": {
    ".": "./dist/index.js",
    "./package.json": "./package.json"
  }
}
```

ESM は CJS と「後方」互換性を持つようになりました。23.0.0 および 22.12.0 以降、CJS モジュールはフラグなしで [ES モジュールを `require()` できる](https://nodejs.org/api/modules.html#loading-ecmascript-modules-using-require) ようになりました。

### CJS ソースと ESM のみのディストリビューション

これは少し工夫が必要ですが、非常に簡単です。新しい標準をターゲットとする古いプロジェクトや、CJS を好むものの異なる環境向けに公開する開発者にとって、これは最適な選択肢となるでしょう。

**動作例**: [cjs-with-esm-distro](https://github.com/JakobJingleheimer/nodejs-module-config-examples/tree/main/packages/cjs/esm-distro)

```json displayName="Minimal package.json"
{
  "name": "cjs-source-with-esm-distribution",
  "main": "./dist/index.mjs"
}
```

```json displayName="Advanced (verbose) package.json"
{
  "name": "cjs-source-with-esm-distribution",
  "type": "commonjs", // current default, but may change
  "engines": { "node": ">=12.22.7" },
  "exports": {
    ".": "./dist/index.mjs",
    "./package.json": "./package.json"
  }
}
```

[`.mjs`](https://nodejs.org/api/esm.html#enabling) ファイル拡張子は切り札です。**他のすべての**設定を上書きし、ファイルを ESM として扱います。このファイル拡張子を使用する必要があるのは、`packageJson.exports.import` はファイルが ESM であることを示すのではなく（一般的な誤解とは反対に）、パッケージのインポート時に使用されるファイルであることを示すだけだからです（ESM は CJS をインポートできます。以下の [Gotchas](#gotchas) を参照してください）。

### CJS ソースと CJS および ESM ディストリビューション

両方の対象に _直接_ 提供し、ディストリビューションがどちらの環境でも「ネイティブ」に動作するようにするには、いくつかの方法があります。

#### 名前付きエクスポートを `exports` に直接アタッチする

古典的な方法ですが、ある程度の高度な技術と工夫が必要です。これは、既存の `module.exports` にプロパティを追加することを意味します（`module.exports` 全体を再割り当てするのではなく）。

**動作例**: [cjs-with-dual-distro (properties)](https://github.com/JakobJingleheimer/nodejs-module-config-examples/tree/main/packages/cjs/dual/property-distro)

```json displayName="Minimal package.json"
{
  "name": "cjs-source-with-esm-via-properties-distribution",
  "main": "./dist/cjs/index.js"
}
```

```json displayName="Advanced (verbose) package.json"
{
  "name": "cjs-source-with-esm-via-properties-distribution",
  "type": "commonjs", // current default, but may change
  "engines": { "node": ">=12.22.7" },
  "exports": {
    ".": "./dist/cjs/index.js",
    "./package.json": "./package.json"
  }
}
```

メリット:

- パッケージサイズが小さい
- 簡単でシンプル (多少の構文上の制約さえ守れば、おそらく最小限の労力で済む)
- [二重パッケージ化の危険性](#the-dual-package-hazard) を回避

デメリット:

- 非常に特殊な構文 (ソースコード内、またはバンドラの扱い方) が必要となる

CJS モジュールは、`module.exports` を別のもの (オブジェクトまたは関数) に再割り当てすることがあります。例:

```cjs
const someObject = {
  foo() {},
  bar() {},
  qux() {},
};

module.exports = someObject;
```

Node.jsは、CJS内の名前付きエクスポートを[特定のパターンを探す静的解析](https://github.com/nodejs/cjs-module-lexer/tree/main?tab=readme-ov-file#parsing-examples)によって検出しますが、上記の例ではこれを回避しています。名前付きエクスポートを検出可能にするには、以下の手順を実行してください。

```cjs
module.exports.foo = function foo() {};
module.exports.bar = function bar() {};
module.exports.qux = function qux() {};
```

#### シンプルな ESM ラッパーを使用する

設定が複雑で、適切なバランスを取るのが困難です。

**動作例**: [cjs-with-dual-distro (ラッパー)](https://github.com/JakobJingleheimer/nodejs-module-config-examples/tree/main/packages/cjs/dual/wrapper-distro)

```json displayName="Minimal package.json"
{
  "name": "cjs-with-wrapper-dual-distro",
  "exports": {
    ".": {
      "import": "./dist/esm/wrapper.mjs",
      "require": "./dist/cjs/index.js",
      "default": "./dist/cjs/index.js"
    }
  }
}
```

```json displayName="Advanced (verbose) package.json"
{
  "name": "cjs-with-wrapper-dual-distro",
  "type": "commonjs",
  "engines": { "node": ">=12.22.7" },
  "exports": {
    ".": {
      "import": "./dist/esm/wrapper.mjs",
      "require": "./dist/cjs/index.js",
      "default": "./dist/cjs/index.js"
    },
    "./package.json": "./package.json"
  }
}
```

メリット:

- パッケージサイズが小さい

デメリット:

- 複雑なバンドラー操作が必要になる可能性が高い（Webpack でこれを自動化する既存のオプションは見つかりませんでした）。

バンドラーからの CJS 出力が Node.js の名前付きエクスポート検出を回避した場合、ESM ラッパーを使用して、ESM コンシューマー向けに既知の名前付きエクスポートを明示的に再エクスポートできます。

CJS がオブジェクト（ESM の `default` にエイリアスされます）をエクスポートする場合、オブジェクトのすべてのメンバーへの参照をラッパー内にローカルに保存し、それらを再エクスポートすることで、ESM コンシューマーが名前ですべてのメンバーにアクセスできるようになります。

```js displayName="./dist/esm/wrapper.mjs"
import cjs from '../cjs/index.js';

const { a, b, c /* … */ } = cjs;

export { a, b, c /* … */ };
```

**ただし**、これはライブバインディングを壊します。`cjs.a` への再割り当ては `esmWrapper.a` に反映されません。

#### 2つのフルディストリビューション

いろいろ詰め込んで、うまくいくことを期待しましょう。これはおそらくCJSからCJSとESMへの変換オプションの中で最も一般的で簡単な方法ですが、費用がかかります。これはあまり良いアイデアではありません。

**動作例**: [cjs-with-dual-distro (double)](https://github.com/JakobJingleheimer/nodejs-module-config-examples/tree/main/packages/cjs/dual/double-distro)

```json displayName="Minimal package.json"
{
  "name": "cjs-with-full-dual-distro",
  "exports": {
    ".": {
      "import": "./dist/esm/index.mjs",
      "require": "./dist/cjs/index.js",
      "default": "./dist/cjs/index.js"
    }
  }
}
```

```json displayName="Advanced (verbose) package.json"
{
  "name": "cjs-with-full-dual-distro",
  "type": "commonjs",
  "engines": { "node": ">=12.22.7" },
  "exports": {
    ".": {
      "import": "./dist/esm/index.mjs",
      "require": "./dist/cjs/index.js",
      "default": "./dist/cjs/index.js"
    },
    "./package.json": "./package.json"
  }
}
```

メリット:

- シンプルなバンドラー設定

デメリット:

- パッケージの重量が大きくなる (実質的に2倍)
- [デュアルパッケージハザード](#the-dual-package-hazard) の脆弱性

代わりに、`"default"` キーと `"node"` キーを使用することもできます。これらは直感的に分かりやすいです。Node.js は常に `"node"` オプション (常に動作します) を選択します。また、Node.js 以外のツールは、node 以外のものをターゲットにするように設定されている場合は `"default"` を選択します。**これにより、デュアルパッケージハザードを回避できます。**

```json displayName="Minimal package.json"
{
  "name": "cjs-with-alt-full-dual-distro",
  "exports": {
    ".": {
      "node": "./dist/cjs/index.js",
      "default": "./dist/esm/index.mjs"
    }
  }
}
```

```json displayName="Advanced (verbose) package.json"
{
  "name": "cjs-with-alt-full-dual-distro",
  "type": "commonjs",
  "engines": { "node": ">=12.22.7" },
  "exports": {
    ".": {
      "node": "./dist/cjs/index.js",
      "default": "./dist/esm/index.mjs"
    },
    "./package.json": "./package.json"
  }
}
```

### ESMソースとCJSディストリビューションのみ

もうカンザスじゃないよ、トト。

設定（2つのオプションがあります）は[ESMソースとCJSとESMディストリビューションの両方](#esm-source-and-both-cjs-amp-esm-distribution)とほぼ同じですが、`packageJson.exports.import`を除外するだけです。

💡 `"type": "module"`[^2]と`.cjs`ファイル拡張子（commonjsファイルの場合）を組み合わせると、最良の結果が得られます。理由の詳細については、以下の[Down the rabbit-hole](#down-the-rabbit-hole)と[Gotchas](#gotchas)をご覧ください。

**動作例**: [esm-with-cjs-distro](https://github.com/JakobJingleheimer/nodejs-module-config-examples/tree/main/packages/esm/cjs-distro)

### ESM ソースと CJS および ESM ディストリビューション

ソースコードが JavaScript 以外（例：TypeScript）で記述されている場合、その言語固有のファイル拡張子（例：`.ts`）を使用する必要があり、`.mjs` に相当する拡張子がない可能性があるため、選択肢が限られることがあります。

[CJS ソースと CJS および ESM ディストリビューション](#cjs-source-and-both-cjs-amp-esm-distribution) と同様に、同じ選択肢があります。

#### プロパティエクスポートを含むCJSディストリビューションのみを公開する

作成が難しく、良質な材料が必要です。

このオプションは、上記の[CJSとESMディストリビューションのプロパティエクスポートを含むCJSソース](#attach-named-exports-directly-onto-raw-exports-endraw-)とほぼ同じです。唯一の違いは、package.jsonの`"type": "module"`です。

この出力の生成をサポートしているのは、一部のビルドツールのみです。[Rollup](https://www.rollupjs.org/)は、commonjsをターゲットにした場合、すぐに互換性のある出力を生成します。[v5.66.0+](https://github.com/webpack/webpack/releases/tag/v5.66.0)以降のWebpackは、新しい[`commonjs-static`](https://webpack.js.org/configuration/output/#type-commonjs-static)出力タイプを使用することで、互換性のある出力を生成します（それより前は、commonjsオプションでは互換性のある出力が生成されません）。現時点では、[esbuild](https://esbuild.github.io/) (非静的な `exports` を生成する) では不可能です。

以下の動作例は Webpack の最新リリース前に作成されたため、Rollup を使用しています (Webpack のオプションも追加する予定です)。

これらの例では、JavaScript ファイルが拡張子 `.js` を使用していることを前提としています。`package.json` の `"type"` によって、それらの解釈方法が制御されます。

`"type":"commonjs"` + `.js` → `cjs`<br />
`"type":"module"` + `.js` → `mjs`

ファイル拡張子が `.cjs` または `.mjs` のみで明示的に指定されている場合（`.js` は使用していない場合）、`"type" は不要です。

**動作例**: [esm-with-cjs-distro](https://github.com/JakobJingleheimer/nodejs-module-config-examples/tree/main/packages/esm/dual/property-distro)

```json displayName="Minimal package.json"
{
  "name": "esm-with-cjs-distribution",
  "type": "module",
  "main": "./dist/index.cjs"
}
```

```json displayName="Advanced (verbose) package.json"
{
  "name": "esm-with-cjs-distribution",
  "type": "module",
  "engines": { "node": ">=12.22.7" },
  "exports": {
    ".": "./dist/index.cjs",
    "./package.json": "./package.json"
  }
}
```

💡 `"type": "module"`[^2] と `.cjs` ファイル拡張子（commonjs ファイル用）を組み合わせると、最良の結果が得られます。理由の詳細については、以下の [Down the rabbit-hole](#down-the-rabbit-hole) と [Gotchas](#gotchas) を参照してください。

#### ESM ラッパーを使用した CJS ディストリビューションを公開する

ここでは多くの処理が行われており、通常は最適な方法ではありません。

これは [ESM ラッパーを使用した CJS ソースとデュアルディストリビューション](#use-a-simple-esm-wrapper) とほぼ同じですが、`"type": "module"` と package.json 内のいくつかの `.cjs` ファイル拡張子がわずかに異なります。

**動作例**: [esm-with-dual-distro (ラッパー)](https://github.com/JakobJingleheimer/nodejs-module-config-examples/tree/main/packages/esm/dual/wrapper-distro)

```json displayName="Minimal package.json"
{
  "name": "esm-with-cjs-and-esm-wrapper-distribution",
  "type": "module",
  "exports": {
    ".": {
      "import": "./dist/esm/wrapper.js",
      "require": "./dist/cjs/index.cjs",
      "default": "./dist/cjs/index.cjs"
    }
  }
}
```

```json displayName="Advanced (verbose) package.json"
{
  "name": "esm-with-cjs-and-esm-wrapper-distribution",
  "type": "module",
  "engines": { "node": ">=12.22.7" },
  "exports": {
    ".": {
      "import": "./dist/esm/wrapper.js",
      "require": "./dist/cjs/index.cjs",
      "default": "./dist/cjs/index.cjs"
    },
    "./package.json": "./package.json"
  }
}
```

💡 `"type": "module"`[^2] と `.cjs` ファイル拡張子（commonjs ファイル用）を組み合わせると、最良の結果が得られます。理由の詳細については、以下の [ウサギの穴に落ちる](#down-the-rabbit-hole) と [落とし穴](#gotchas) を参照してください。

#### CJS と ESM の両方の完全なディストリビューションを公開する

（サプライズ付きの）いくつかのものを詰め込んで、うまくいくことを期待します。これは、ESM から CJS と ESM へのオプションの中でおそらく最も一般的で簡単な方法ですが、費用がかかります。これはあまり良いアイデアではありません。

パッケージ構成に関しては、主に個人の好みによって異なるいくつかのオプションがあります。

##### パッケージ全体を ESM としてマークし、CJS エクスポートを `.cjs` ファイル拡張子で CJS として明示的にマークします。

このオプションは、開発者の負担が最も少ない方法です。

これはまた、ビルドツールが `.cjs` ファイル拡張子を持つ配布ファイルを生成する必要があることを意味します。そのため、複数のビルドツールを連結したり、ファイルを移動/名前変更して `.cjs` ファイル拡張子を持つようにする後続の手順を追加したりする必要がある可能性があります (例: `mv ./dist/index.js ./dist/index.cjs`)。この問題は、出力されたファイルを移動/名前変更する後続の手順を追加することで回避できます (例: [Rollup](https://rollupjs.org/) または [シンプルなシェルスクリプト](https://stackoverflow.com/q/21985492))。

`.cjs` ファイル拡張子のサポートは 12.0.0 で追加されました。これを使用すると、ESM はファイルを commonjs として正しく認識します（`import { foo } from './foo.cjs'` は動作します）。ただし、`require()` は `.js` のように `.cjs` を自動解決しないため、commonjs で一般的に行われているようにファイル拡張子を省略することはできません。`require('./foo')` は失敗しますが、`require('./foo.cjs')` は動作します。パッケージのエクスポートでこれを使用してもデメリットはありません。`packageJson.exports`（および `packageJson.main`）はファイル拡張子を必須とし、ユーザーは package.json の `"name"` フィールドでパッケージを参照します（そのため、ユーザーはこのことを全く意識しません）。

**動作例**: [esm-with-dual-distro](https://github.com/JakobJingleheimer/nodejs-module-config-examples/tree/main/packages/esm/dual/double-distro)

```json displayName="Minimal import & require package.json"
{
  "type": "module",
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

```json displayName="Advanced (verbose) import & require package.json"
{
  "type": "module",
  "engines": { "node": ">=12.22.7" },
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/index.cjs"
    },
    "./package.json": "./package.json"
  }
}
```

あるいは、直感に反しない `"default"` キーと `"node"` キーを使用することもできます。Node.js は常に `"node"` オプション（常に機能します）を選択し、Node.js 以外のツールは、node 以外のものをターゲットにするように構成されている場合は `"default"` を選択します。**これにより、二重パッケージの危険性が排除されます。**

```json displayName="Minimal default & node package.json"
{
  "type": "module",
  "exports": {
    ".": {
      "node": "./dist/index.cjs",
      "default": "./dist/esm/index.js"
    }
  }
}
```

```json displayName="Advanced (verbose) default & node package.json"
{
  "type": "module",
  "engines": { "node": ">=12.22.7" },
  "exports": {
    ".": {
      "node": "./dist/index.cjs",
      "default": "./dist/esm/index.js"
    },
    "./package.json": "./package.json"
  }
}
```

💡 `"type": "module"`[^2] と `.cjs` ファイル拡張子（commonjs ファイル用）を組み合わせると、最良の結果が得られます。理由の詳細については、以下の [Down the rabbit-hole](#down-the-rabbit-hole) と [Gotchas](#gotchas) を参照してください。

##### すべてのソースコードファイルには `.mjs`（または同等の）ファイル拡張子を使用してください。

この設定は、[CJS ソースおよび CJS と ESM の両方のディストリビューション](#cjs-source-and-both-cjs-amp-esm-distribution) と同じです。

**JavaScript 以外のソースコード**: JavaScript 以外の言語独自の設定で、入力ファイルが ESM であることを認識/指定する必要があります。

#### Node.js 12.22.x より前

🛑 実行しないでください: Node.js 12.x より前のバージョンはサポート終了となり、深刻なセキュリティ上の脆弱性が存在します。

セキュリティ研究者の方で、Node.js 12.22.x より前のバージョンを調査する必要がある場合は、設定のサポートについてお気軽にお問い合わせください。

## 一般的な注意事項

[構文検出](https://nodejs.org/api/packages.html#syntax-detection)は、適切なパッケージ構成の代替手段ではありません。構文検出は完全なものではなく、[パフォーマンスに大きな影響](https://github.com/nodejs/node/pull/55238)を伴います。

package.jsonで[`"exports"`](https://nodejs.org/api/packages.html#conditional-exports)を使用する場合は、一般的に`"./package.json": "./package.json"`をインポートできるように含めることが推奨されます（[`module.findPackageJSON`](https://nodejs.org/api/module.html#modulefindpackagejsonspecifier-base)はこの制限の影響を受けませんが、`import`の方が便利な場合があります）。

`"exports"` は [`"main"`](https://nodejs.org/api/packages.html#main) よりも推奨されます。これは、外部から内部コードへのアクセスを阻止するためです（そのため、ユーザーが依存すべきでないものに依存していないことを比較的確実に確認できます）。それが不要な場合は、`"main" の方がシンプルで、より適切な選択肢となる可能性があります。

`"engines"` フィールドは、パッケージがどのバージョンの Node.js と互換性があるかを、人間とマシンの両方にとって分かりやすい形で示します。使用するパッケージマネージャーによっては、ユーザーが互換性のないバージョンの Node.js を使用している場合、例外がスローされ、インストールが失敗することがあります（これはユーザーにとって非常に役立ちます）。このフィールドを含めることで、古いバージョンの Node.js を使用しているためにパッケージを使用できないユーザーの負担を大幅に軽減できます。

## ウサギの穴に落ちろ

Node.js に関しては、特に解決すべき問題が4つあります。

- ソースコードファイルのフォーマットを決定する（作者が自身のコードを実行する）

- 配布ファイルのフォーマットを決定する（利用者が受け取るコード）

- 配布コードを `require()` で読み込めるように公開する（利用者は CJS を期待している）

- 配布コードを `import` で読み込めるように公開する（利用者はおそらく ESM を希望している）

⚠️ 最初の2つは、最後の2つとは **独立** しています。

ファイルの読み込み方法は、ファイルの解釈形式を決定するものではありません。

- **package.json** の **`exports.require`** は **`CJS`** とは逆です。`require()` は、ファイルを盲目的に CJS として解釈することはできず、またそうでもありません。例えば、`require('foo.json')` は、ファイルを CJS ではなく JSON として正しく解釈します。`require()` 呼び出しを含むモジュールは当然 CJS である必要がありますが、ロードするものも必ずしも CJS であるとは限りません。
- **package.json** の **`exports.import`** は **`ESM`** とは逆です。`import` も同様に、ファイルを盲目的に ESM として解釈することはできず、またそうでもありません。`import` は、ESM だけでなく、CJS、JSON、WASM もロードできます。`import` 文を含むモジュールは当然 ESM である必要がありますが、ロードするものも必ずしも ESM であるとは限りません。

したがって、`require` や `import` で引用または命名された設定オプションを目にした場合でも、それらが CJS と ES モジュールを _判別_ するためのものだと決めつけるのはやめましょう。

⚠️ パッケージの設定に `"exports"` フィールド/フィールドセットを追加すると、エクスポートのサブパスに明示的にリストされていないものについては、実質的に [パッケージへの深いパスをブロック](https://nodejs.org/api/packages.html#package-entry-points) されます。つまり、これは破壊的な変更となる可能性があります。

⚠️ CJS と ESM の両方を配布するかどうかは慎重に検討してください。[二重パッケージの危険性](#the-dual-package-hazard) が発生する可能性があります (特に設定が誤っていて、ユーザーが巧妙に操作しようとした場合)。これは、特にパッケージが完全に設定されていない場合、利用プロジェクトで非常に混乱を招くバグにつながる可能性があります。消費者は、あなたのパッケージとは別のフォーマットを使用する中間パッケージによって、不意打ちを受ける可能性があります（例えば、消費者はESMディストリビューションを使用しており、消費者自身も使用している別のパッケージがCJSディストリビューションを使用している場合など）。パッケージが何らかの形でステートフルである場合、CJSとESMディストリビューションの両方を使用すると、並列状態が発生します（これはほぼ確実に意図的ではありません）。

### 二重パッケージの危険性

アプリケーションがCommonJSとESモジュールソースの両方を提供するパッケージを使用している場合、パッケージの両方のインスタンスがロードされると、特定のバグが発生するリスクがあります。この危険性は、`const pkgInstance = require('pkg')` によって作成された `pkgInstance` が、`import pkgInstance from 'pkg'` (または `'pkg/module'` のような代替メインパス) によって作成された `pkgInstance` と同じではないことに起因します。これが「二重パッケージの危険性」であり、同じランタイム環境内に同じパッケージの2つのインスタンスがロードされる可能性があります。アプリケーションやパッケージが意図的に両方のインスタンスを直接ロードすることはほとんどありませんが、アプリケーションが一方のインスタンスをロードし、アプリケーションの依存関係がもう一方のインスタンスをロードすることはよくあります。Node.jsはCommonJSとESモジュールの混在をサポートしているため、この危険性が発生し、予期せぬ混乱を招く動作につながる可能性があります。

パッケージのメインエクスポートがコンストラクタの場合、2つのコピーによって作成されたインスタンスの `instanceof` 比較は `false` を返します。また、エクスポートがオブジェクトの場合、一方に追加されたプロパティ（`pkgInstance.foo = 3` など）はもう一方には存在しません。これは、それぞれ all-CommonJS または all-ES モジュール環境における `import` および `require` ステートメントの動作とは異なるため、ユーザーにとって意外な結果となります。また、これは [Babel](https://babeljs.io/) や [`esm`](https://github.com/standard-things/esm#readme) などのツールを介してトランスパイルを行う際にユーザーが慣れ親しんでいる動作とも異なります。

### これまでの経緯

[CommonJS (CJS)](https://wiki.commonjs.org/wiki/Modules) は、ECMAScript Modules (ESM) よりずっと前に、JavaScript がまだ発展途上だった頃に開発されました。CJS と jQuery の開発期間はわずか 3 年しか離れていません。CJS は公式の ([TC39](https://tc39.es)) 標準ではなく、限られたプラットフォーム (特に Node.js) でのみサポートされています。ESM の標準規格化は数年前から進められており、現在ではすべての主要プラットフォーム (ブラウザ、Deno、Node.js など) でサポートされているため、ほぼすべてのプラットフォームで動作します。ESM が CJS (現在でも非常に人気があり広く普及しています) の後継となることが明らかになったため、多くの人が早期に、多くの場合は ESM 仕様の特定の側面が完成する前から、ESM の採用を試みてきました。そのため、より良い情報が入手できるようになるにつれて（多くの場合、熱心な開発者たちの学習や経験に基づいて）、それらは時間の経過とともに変化し、推測から仕様に沿ったものへと変化しました。

さらに複雑なのは、歴史的にこの領域の多くを管理してきたバンドラーの存在です。しかし、以前はバンドラーに管理させる必要があった機能の多くは、今ではネイティブ機能になっています。それでも、バンドラーは依然として（そしておそらくこれからも）一部の用途では必要です。残念ながら、バンドラーがもはや提供する必要がなくなった機能は、古いバンドラーの実装に深く根付いているため、時には役立ちすぎたり、場合によってはアンチパターンになったりすることがあります（ライブラリのバンドルは、バンドラーの作者自身によって推奨されていないことが多いです）。その仕組みと理由については、それ自体が一つの記事になるほどで​​す。

## 注意点

`package.json` の `"type"` フィールドは、`.js` ファイル拡張子をそれぞれ `commonjs` または ES `module` のいずれかに変更します。CJS と ESM の両方を含むデュアル/混合パッケージでは、このフィールドを誤って使用することが非常によくあります。

```json displayName="⚠️ THIS DOES NOT WORK"
{
  "type": "module",
  "main": "./dist/CJS/index.js",
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.js",
      "default": "./dist/cjs/index.js"
    },
    "./package.json": "./package.json"
  }
}
```

これは動作しません。`"type": "module"` により、`packageJson.main`、`packageJson.exports["."].require`、`packageJson.exports["."].default` が ESM として解釈されてしまうためです（ただし、これらは実際には CJS です）。

`"type": "module"` を除外すると、逆の問題が発生します。

```json displayName="⚠️ THIS DOES NOT WORK"
{
  "main": "./dist/CJS/index.js",
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.js",
      "default": "./dist/cjs/index.js"
    },
    "./package.json": "./package.json"
  }
}
```

これは動作しません。`packageJson.exports["."].import` は CJS として解釈されるからです（実際には ESM です）。

[^1]: Node.js v13.0～13.6 には、`packageJson.exports["."]` が、最初の項目として詳細な設定オプション（オブジェクト）を、2 番目の項目として “default” （文字列）を含む配列である必要があるというバグがありました。[nodejs/modules#446](https://github.com/nodejs/modules/issues/446) を参照してください。

[^2]: package.json の `"type"` フィールドは、`.js` ファイル拡張子の意味を変更します。これは、[HTML スクリプト要素の type 属性](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/script#attr-type) と同様です。
